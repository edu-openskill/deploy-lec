배포, 처음부터 끝까지

로컬에서 개발하던 당신이, 서비스를 세상에 올리기까지 — 강사 없이 혼자 읽어도 이해되는 교재.

0부 왜 배포가 막막한가

처음 배포를 접할 때 느끼는 막막함은 개념이 부족해서가 아닙니다. 오히려 우리는 이미 꽤 많이 알고 있습니다. HTTP가 뭔지 알고, 데이터베이스 쿼리를 짤 줄 알고, Spring Boot 서버를 로컬에서 띄워본 경험도 있습니다. 그런데도 배포 앞에서 막히는 이유는 로컬 개발 환경이 우리도 모르게 수많은 것들을 대신 해주고 있었기 때문입니다. 배포는 그 자동으로 처리되던 것들을 처음으로 직접 마주하는 순간입니다.

"내 컴에선 되는데" — 이 말의 진짜 의미

팀 프로젝트나 인턴십에서 한 번쯤은 이 상황을 겪게 됩니다. 로컬에서 완벽하게 작동하던 기능이 서버에 올리면 500 에러를 내뿜습니다. 분명 코드는 같은데 말이죠. "내 컴에선 되는데"라는 말은 사실 엄청난 정보를 담고 있습니다. 그 말은 곧 "내 컴퓨터의 환경에서는 되는데, 서버의 환경에서는 안 된다"는 뜻입니다. 문제는 코드가 아니라 환경의 차이에 있는 것입니다.

그렇다면 로컬 환경에는 어떤 암묵적인 전제가 깔려 있을까요? 우리가 개발할 때 당연하게 여겼지만, 서버에는 없는 것들을 하나씩 꺼내봅시다.

암묵적 전제 1 — 항상 켜진 내 PC

로컬 서버는 내가 IntelliJ에서 초록색 ▶ 버튼을 누를 때만 살아납니다. 노트북 덮개를 닫으면 죽고, 재부팅하면 없어지고, 자리를 비우면 접근할 수 없습니다. 이걸 당연하게 여겼던 이유는 개발 중에는 항상 내가 거기 앉아 있었기 때문입니다.

하지만 진짜 서비스는 하루 24시간, 일 년 365일 살아 있어야 합니다. 사용자가 새벽 2시에 앱을 열어도, 명절에 가족 모임을 하는 동안에도 서버는 응답해야 합니다. 이를 위해서는 절대 꺼지지 않는 별도의 컴퓨터가 필요하고, 우리는 그것을 서버(server) 혹은 인스턴스(instance)라고 부릅니다. AWS의 EC2, Railway의 컨테이너, 학교 전산실의 서버 모두 같은 역할입니다. 내 노트북이 아닌, 어딘가에 24시간 켜져 있는 컴퓨터입니다.

짚고 가기 서버는 특별한 컴퓨터가 아닙니다. CPU와 메모리와 디스크가 있는, 그냥 컴퓨터입니다. 다만 절대 꺼지지 않는, 인터넷에 연결된, 내가 아닌 누군가(혹은 클라우드 회사)가 관리하는 컴퓨터입니다.

암묵적 전제 2 — localhost로 바로 접속

개발 중에는 브라우저 주소창에 http://localhost:8080을 입력합니다. localhost는 "지금 내가 사용하는 이 컴퓨터"를 의미하는 특별한 주소입니다. 서버가 어디 있든 찾아갈 필요가 없습니다. 코드도, 서버도, 클라이언트도 모두 같은 기계 위에 있으니까요.

하지만 서버가 멀리 있는 다른 컴퓨터로 옮겨가는 순간, 이 주소는 의미를 잃습니다. 그 서버에서 localhost는 그 서버 자신을 가리키지, 내 노트북을 가리키지 않습니다. 이제 외부에서 서버에 접근하려면 그 서버의 공인 IP 주소(예: 43.202.58.11)나 도메인 이름(예: api.myapp.com)이 필요합니다. 그리고 그 주소가 실제 서버로 연결되려면 DNS, 방화벽, 포트 설정이 맞물려야 합니다 — 1부에서 그 흐름 전체를 지도로 살펴볼 예정입니다.

암묵적 전제 3 — IDE가 알아서 빌드하고 실행한다

IntelliJ에서 ▶ 버튼을 누르면 무슨 일이 일어날까요? 사실 IDE는 그 순간 엄청나게 많은 일을 조용히 처리합니다. 소스 코드를 컴파일하고, 클래스 파일들을 묶고, application.properties를 읽어 설정을 주입하고, 내장 Tomcat을 실행합니다. 우리는 그 모든 단계를 버튼 하나로 위임했던 것입니다.

서버에는 IntelliJ가 없습니다. 서버는 우리가 빌드한 결과물인 app.jar 파일 하나를 받아서, java -jar app.jar라는 명령 하나로 실행합니다. 따라서 배포 전에 반드시 빌드라는 과정이 필요합니다. Spring Boot 프로젝트라면 ./gradlew build를 실행하면 build/libs/app.jar라는 파일이 만들어집니다. 이 파일 하나 안에 우리 서버의 전부가 담겨 있습니다 — 컴파일된 코드, 설정 파일, 심지어 Tomcat 서버까지도요. 이것이 빌드 산출물(artifact)입니다.

흔한 실수 ./gradlew build를 실행하지 않고, 소스 코드(.java 파일들)를 그대로 서버에 올리려는 경우가 있습니다. 서버에는 개발 도구가 없으므로 소스 코드 자체로는 실행할 수 없습니다. 서버에 올라가야 하는 것은 소스 코드가 아니라, 빌드된 JAR 파일입니다.

암묵적 전제 4 — 내 PC에만 깔린 JDK와 DB

로컬에서 서버를 실행할 수 있었던 이유 중 하나는 언제가 내 컴퓨터에 Java JDK를 설치했기 때문입니다. 아마도 몇 달 전, 처음 개발 환경을 세팅할 때 설치 가이드를 따라 JDK 17이나 21을 설치했을 것입니다. 데이터베이스도 마찬가지입니다. MySQL이나 PostgreSQL을 로컬에 설치했거나, Docker로 컨테이너를 띄워 사용하고 있었을 것입니다.

빈 우분투 서버에는 아무것도 없습니다. java도 없고, mysql도 없습니다. java -jar app.jar를 실행하면 "command not found"라는 메시지만 나옵니다. 그래서 배포의 상당 부분은 사실 "서버에 필요한 것들을 설치하고 설정하는 작업"입니다. JDK를 설치하고, DB 서버를 구성하거나 관리형 DB 서비스(RDS 등)에 연결하고, 환경 변수를 세팅하는 것들이 모두 여기에 해당합니다.

여기서 Docker와 컨테이너가 강력한 이유가 드러납니다. Dockerfile에 "Ubuntu 위에 JDK 21 깔고, 이 JAR 파일을 복사하고, 이 명령으로 실행해"라고 적어두면, 어떤 서버에서도 동일한 환경이 재현됩니다. "내 컴에선 되는데"를 원천 차단하는 도구가 바로 컨테이너입니다. (컨테이너는 2부에서 더 자세히 다룹니다.)

배포의 멘탈모델: 재현의 예술

이 네 가지 전제를 꺼내놓고 나면, 배포의 본질이 선명해집니다.

배포란, 내 로컬 환경의 암묵적 전제들을 남의 컴퓨터(서버)에 명시적으로 다시 만들어주는 일입니다.

내 컴퓨터에서는 자동으로, 암묵적으로 갖춰져 있던 것들을 — 항상 켜진 프로세스, 접근 가능한 주소, 빌드된 실행 파일, 설치된 런타임 — 서버라는 낯선 땅에 하나씩 명시적으로 심어야 합니다. 이것이 배포입니다.

그렇게 생각하면, 배포 과정에서 마주치는 모든 오류는 대부분 이 네 가지 전제 중 하나를 빠트렸거나 잘못 설정했을 때 발생합니다. "포트가 안 열렸다"는 전제 2의 문제, "java: command not found"는 전제 4의 문제, "서버가 재부팅 후 안 뜬다"는 전제 1의 문제입니다. 앞으로 에러를 만날 때마다 이 네 가지 전제를 머릿속에 떠올려보세요. 어느 전제가 서버에 아직 만들어지지 않은 것인지 점검하면, 막막한 문제가 훨씬 구체적으로 보이기 시작합니다.

한 줄 정리 배포 = 로컬의 암묵적 전제(항상 켜진 PC / localhost / IDE 빌드 / JDK·DB)를 서버에 명시적으로 재현하는 일. "내 컴에선 되는데"는 두 환경의 차이를 아직 메우지 않았다는 신호다.

1부 배포의 전체 그림

배포란 코드가 로컬 머신을 떠나 인터넷을 통해 사용자에게 도달하기까지의 전체 경로를 이해하는 일입니다. 0부에서 우리는 로컬의 암묵적 전제 네 가지를 해부했습니다. 이번 부에서는 그 전제들이 실제 서버 환경에서 어떤 부품들로 채워지는지, 요청 한 번이 사용자의 손가락 끝에서 데이터베이스까지 어떤 여정을 거치는지 전체 지도를 펼쳐보겠습니다. 이 지도를 한 번 머릿속에 그려두면, 앞으로 어떤 배포 문서나 에러 로그를 봐도 "지금 이 문제는 이 화살표에서 벌어지고 있구나"라고 위치를 잡을 수 있게 됩니다.

요청 한 번의 여정 — 이야기로 읽기

Flutter 앱이 설치된 사용자의 스마트폰을 상상해보세요. 사용자가 "내 피드 불러오기" 버튼을 탭합니다. 이 순간부터 무슨 일이 일어날까요?

앱 안에는 API 주소가 적혀 있습니다: https://api.myapp.com/feed. 앱은 이 주소로 HTTP 요청을 보내야 하는데, 먼저 api.myapp.com이 어느 서버인지 알아야 합니다. 스마트폰은 DNS 서버에 물어봅니다. "api.myapp.com 은 어디야?" DNS 서버는 대답합니다. "43.202.58.11이야." 이제 앱은 그 IP 주소로 패킷을 보냅니다.

패킷이 인터넷을 건너 서버에 도착합니다. 서버 앞에는 보안그룹(Security Group)이라는 관문이 있습니다. 클라우드가 제공하는 방화벽입니다. 이 관문은 목록을 확인합니다. "443 포트로 오는 요청은 통과." 요청은 서버 안으로 들어옵니다.

서버 안에서 가장 먼저 요청을 받는 것은 Nginx입니다. Nginx는 리버스 프록시(reverse proxy) 역할을 합니다. "나는 443 포트에서 HTTPS 요청을 받는 관리자야. 요청이 오면 내부의 8080 포트로 넘겨줄게." Nginx는 TLS 암호화도 풀어줍니다(HTTPS → HTTP). 이제 요청은 평문 HTTP가 되어 내부망에서 8080 포트로 전달됩니다.

8080 포트에는 Spring Boot JAR 프로세스가 떠 있습니다. java -jar app.jar로 실행된 우리의 서버입니다. 이 프로세스가 요청을 받아 비즈니스 로직을 처리하고, 필요하다면 데이터베이스에 쿼리를 보냅니다. DB가 응답을 주면, JAR이 JSON을 만들어 역순으로 응답을 돌려보냅니다. 결국 사용자의 스마트폰에는 피드 목록이 나타납니다.

핵심 개념 8개 — 화살표별 주인공

지도의 각 구간을 담당하는 개념들을 이제 하나씩 뜯어봅니다. 각 개념은 "왜 이것이 필요한가"부터 시작합니다.

① 빌드 산출물(Artifact) — JAR 파일

로컬에서 ▶ 버튼을 누르면 IntelliJ가 수백 개의 .java 파일을 컴파일해서 실행합니다. 서버에는 IntelliJ도 없고, Gradle도 없고, 소스 코드를 이해하는 도구도 없습니다. 그래서 우리는 미리 소스 코드를 "실행 가능한 하나의 파일"로 만들어서 서버에 가져다 주어야 합니다. 그것이 빌드 산출물, 줄여서 아티팩트(artifact)입니다.

Spring Boot의 경우 ./gradlew build 명령을 실행하면 build/libs/app.jar 파일이 생성됩니다. JAR(Java ARchive)은 컴파일된 클래스 파일들, 리소스 파일들, 그리고 놀랍게도 Tomcat 서버까지 하나의 ZIP 파일 안에 묶은 것입니다. 이 파일 하나가 우리 서버의 전부입니다. java -jar app.jar 명령 하나로 서버가 떠오릅니다.

짚고 가기 Spring Boot의 "실행 가능한 JAR(executable JAR)"은 Fat JAR 혹은 Uber JAR이라고도 불립니다. 의존 라이브러리(.jar 수십 개)가 모두 안에 포함되어 있어서, 서버에 JDK만 있으면 외부 라이브러리 없이도 단독으로 실행됩니다. 전통적인 WAR + 외장 Tomcat 방식과 대조됩니다.

② 실행 환경(Runtime) — JVM

JAR 파일이 있어도, java 명령이 없으면 실행할 수 없습니다. Java 코드는 CPU가 직접 실행하는 기계어가 아니라, JVM(Java Virtual Machine)이 해석하는 바이트코드로 컴파일됩니다. 따라서 서버에는 반드시 JDK(또는 JRE)가 설치되어 있어야 합니다.

버전도 중요합니다. 로컬에서 JDK 21로 빌드한 JAR은 서버의 JRE 11에서 실행되지 않을 수 있습니다. UnsupportedClassVersionError라는 무시무시한 오류가 기다리고 있습니다. 배포 체크리스트에는 항상 "서버의 Java 버전이 빌드 환경과 일치하는가"를 확인하는 항목이 있어야 합니다.

흔한 실수 로컬은 JDK 21, 서버는 JDK 11. 빌드는 성공했지만 서버에서 실행 시 UnsupportedClassVersionError가 발생합니다. 서버에 설치된 Java 버전을 java -version으로 먼저 확인하고, 프로젝트의 build.gradle 혹은 pom.xml에 명시된 sourceCompatibility와 맞추세요.

③ 프로세스와 포트 — 문 번호

서버에서 java -jar app.jar를 실행하면 하나의 프로세스(process)가 생깁니다. 운영체제가 이 프로세스에 PID(프로세스 ID)를 부여합니다. 프로세스는 포트(port)를 열고 대기합니다. Spring Boot의 기본 포트는 8080입니다.

포트는 서버 컴퓨터 안에서 "어느 프로세스에게 전달할 것인가"를 구분하는 문 번호라고 생각하면 됩니다. 항구(port)에 여러 개의 부두가 있고, 각 부두에 배가 정박하는 것과 같습니다. 하나의 서버에 여러 서비스가 떠 있다면 각각 다른 포트를 씁니다. 예: Spring Boot API는 8080, Redis는 6379, MySQL은 3306.

이미 다른 프로세스가 8080을 사용하고 있다면 "Address already in use" 에러가 납니다. lsof -i :8080 (Linux/Mac) 또는 netstat -ano | findstr :8080 (Windows)으로 어떤 프로세스가 포트를 쥐고 있는지 확인할 수 있습니다.

④ 공인 IP vs 사설 IP — 두 가지 주소

집 안 와이파이에 연결된 기기들은 모두 192.168.x.x 같은 주소를 가집니다. 이것이 사설 IP(private IP)입니다. 외부 인터넷에서는 이 주소로 직접 접근할 수 없습니다. 반면 공인 IP(public IP)는 인터넷 전체에서 유일한 주소입니다. 집 전체가 공유하는 공유기 주소처럼, 외부에서 찾아올 수 있는 진짜 주소입니다.

AWS EC2 서버를 생성하면 두 가지 IP가 부여됩니다. 공인 IP(예: 43.202.58.11)는 외부 인터넷에서 접근할 수 있는 주소이고, 사설 IP(예: 172.31.12.5)는 같은 VPC(가상 네트워크) 안에서 통신할 때 사용합니다. DB 서버는 외부에 공인 IP를 노출하지 않고 사설 IP로만 접근하도록 구성하는 것이 보안의 기본입니다.

흔한 실수 EC2를 재시작하면 공인 IP가 바뀝니다. 코드에 IP 주소를 하드코딩해두면 재시작 때마다 배포가 깨집니다. 고정 IP가 필요하다면 Elastic IP를 할당하거나, 처음부터 도메인을 연결해서 사용하세요(3부 참고).

⑤ 방화벽과 보안그룹 — 어떤 포트를 열 것인가

서버에 공인 IP가 생겼다고 해서 아무 포트로나 접근할 수 있는 것은 아닙니다. 서버 앞에는 방화벽(firewall)이 서 있습니다. AWS에서는 이것을 보안그룹(Security Group)이라고 부릅니다. 보안그룹은 인바운드(inbound) 규칙으로 "어떤 출처에서, 어떤 프로토콜로, 어떤 포트로 오는 요청을 허용할 것인가"를 정의합니다.

기본 상태에서 보안그룹은 대부분의 포트를 닫아 놓습니다. 웹 서버를 운영하려면 최소한 80(HTTP)과 443(HTTPS) 포트를 열어야 하고, SSH 접속을 위해 22 포트도 허용해야 합니다. Spring Boot 포트인 8080은 Nginx 뒤에 숨기는 것이 일반적이므로 외부에 열지 않아도 됩니다. "배포는 했는데 접속이 안 된다"는 상황의 절반은 보안그룹 포트를 안 열었기 때문입니다.

⑥ DNS — 주소창의 마법

사람은 43.202.58.11을 외울 수 없습니다. 그래서 DNS(Domain Name System)가 있습니다. DNS는 인터넷의 전화번호부입니다. api.myapp.com을 입력하면 DNS 서버가 그에 대응하는 IP를 알려줍니다.

도메인을 구매한 후, DNS 제공사(AWS Route 53, 가비아, 클라우드플레어 등)에서 A 레코드를 설정합니다. A 레코드는 "이 도메인 이름을 이 IP 주소로 연결해"라는 단순한 지시입니다. DNS 설정이 전 세계 DNS 서버에 전파되는 데 최대 48시간이 걸릴 수 있습니다(보통은 수분~수십 분). 도메인을 등록했는데 "바로 안 된다"고 놀라지 마세요 — 전파 중일 뿐입니다. DNS의 자세한 동작은 3부에서 다룹니다.

⑦ 리버스 프록시 — 43번 창구가 대신 받는다

브라우저와 앱은 기본적으로 HTTPS라면 443 포트로 요청을 보냅니다. 그런데 우리 Spring Boot는 8080에서 돌고 있습니다. 이 불일치를 해결하는 것이 리버스 프록시(reverse proxy)입니다.

Nginx는 443 포트에서 외부 요청을 받고, 내부적으로 http://localhost:8080으로 전달(proxy_pass)합니다. 클라이언트 입장에서는 항상 443으로 통신하므로 내부 구조를 알 필요가 없습니다. 리버스 프록시가 주는 이점은 하나뿐이 아닙니다. 하나의 서버에서 여러 도메인의 요청을 포트별로 분기할 수 있고, 정적 파일을 직접 서빙할 수 있고, 요청 속도 제한(rate limiting), 로드 밸런싱, 캐싱까지 Nginx 레벨에서 처리할 수 있습니다.

짚고 가기 "프록시(proxy)"는 "대리인"입니다. 포워드 프록시는 클라이언트를 대신해 외부로 나가고(회사 내부망의 인터넷 게이트웨이), 리버스 프록시는 서버를 대신해 클라이언트를 받습니다(Nginx). 방향이 반대입니다.

⑧ TLS 인증서 — 자물쇠의 정체

브라우저 주소창 왼쪽의 자물쇠 아이콘, 앱이 통신하는 HTTPS — 이것들을 가능하게 하는 것이 TLS(Transport Layer Security) 인증서입니다. TLS는 두 가지 일을 합니다. 첫째, 서버가 진짜 api.myapp.com이라는 것을 인증서로 증명합니다(위변조 방지). 둘째, 클라이언트와 서버 사이의 모든 데이터를 암호화합니다(도청 방지).

인증서는 공신력 있는 기관(CA, Certificate Authority)이 발급합니다. Let's Encrypt는 무료로 자동 발급·갱신을 해주는 CA입니다. AWS를 쓴다면 ACM(AWS Certificate Manager)이 무료로 인증서를 관리해줍니다. HTTPS는 선택이 아닙니다. Apple App Store와 Google Play 모두 앱이 평문 HTTP 통신을 하는 것을 기본적으로 차단합니다. 배포 체크리스트에서 HTTPS는 필수 항목입니다.

이제 지도의 모든 화살표에 이름이 생겼습니다. 아래에서 요청 한 번이 각 관문을 통과하는 과정을 단계별로 따라가 보세요. 특히 보안그룹 단계를 눈여겨보세요 — "배포는 했는데 접속이 안 된다"는 상황의 대부분이 바로 여기서 일어납니다. (각 관문이 실제로 어떻게 열리고 막히는지는 2부의 EC2 시뮬레이터에서 직접 실행해볼 수 있습니다.)

1
📱 앱이 api.myapp.com/feed 로 요청
앱에 적힌 baseURL을 향해 HTTPS 요청을 출발시킵니다.
2
🔎 DNS — "api.myapp.com이 어디야?"
DNS 서버가 A 레코드를 보고 답합니다: "43.202.58.11이야." 이제 패킷이 그 IP로 인터넷을 건너갑니다.
3
🛡 보안그룹 — 포트 검문소
인바운드 규칙을 확인합니다. "443 포트 허용? → 통과." 허용 규칙이 없는 포트로 온 요청은 응답조차 없이 버려집니다.
⚠ 닫혀 있으면 여기서 차단 — "배포했는데 접속 안 됨"의 주범
4
🚪 Nginx — 443에서 받아 8080으로
TLS 암호화를 풀고(HTTPS→HTTP), 내부의 8080 포트로 요청을 넘깁니다(proxy_pass).
5
☕ Spring Boot JAR :8080
비즈니스 로직을 처리하고 필요하면 DB에 쿼리를 보냅니다.
6
🗄 DB → 역순으로 응답
DB 응답 → JAR이 JSON 생성 → Nginx → 인터넷 → 앱 화면에 피드가 나타납니다.
요청의 여정 6단계 — 화살표 하나하나가 배포의 관문
한 줄 정리 요청 한 번의 여정: 앱 → DNS(도메인→IP 번역) → 공인IP → 보안그룹(방화벽) → Nginx(리버스 프록시·TLS 해제) → JAR:8080(비즈니스 로직) → DB. 각 화살표를 막는 것 하나하나가 배포의 관문이다.

2부 백엔드 올리기 — 자동화 사다리

수동 배포에서 GitOps 완전 자동화까지, 자동화 사다리를 한 칸씩 올라가며 각 단계의 책임 분담을 파악합니다. 이 부의 핵심 질문은 하나입니다: "이 작업을 내가 직접 할 것인가, 아니면 플랫폼에 위임할 것인가?" 사다리를 올라갈수록 내 손이 적게 가고 플랫폼이 많이 대신해줍니다. 단, 위임에는 항상 트레이드오프가 있습니다 — 편리함 대신 제어권을 내놓는 것입니다.

이 부에서는 똑같은 app.jar 하나를 네 가지 방식으로 올려봅니다. 코드는 바뀌지 않습니다. 바뀌는 것은 "누가 어디까지 해주는가"입니다.

JAR이란 무엇인가 — 배포의 기본 단위

모든 출발점은 JAR 파일입니다. Spring Boot 프로젝트의 루트 디렉터리에서 다음 명령을 실행합니다:

  • ./gradlew build (Gradle 프로젝트) 또는 mvn package (Maven 프로젝트)
  • 빌드가 완료되면 build/libs/app.jar 또는 target/app.jar 파일이 생성됩니다.

이 파일 하나가 서버의 전부입니다. 안에는 컴파일된 클래스 파일, 설정 파일, 그리고 내장 Tomcat 서버까지 모두 포함되어 있습니다. 서버에서 java -jar app.jar를 실행하면 Spring Boot가 기동되고 8080 포트에서 요청을 기다립니다. 얼마나 단순합니까 — JAR 하나, 명령 하나.

그렇다면 이 단순한 JAR을 서버에 올리는 것이 왜 처음에는 그렇게 어렵게 느껴질까요? 이제 사다리의 첫 번째 칸부터 직접 경험해봅시다.

1단계 — AWS EC2에 손으로: 모든 걸 내가 한다

AWS 콘솔에 접속해서 EC2 인스턴스를 하나 생성합니다. Ubuntu 22.04, t2.micro(프리티어). 이 빈 우분투 서버에는 정말 아무것도 없습니다. 여기서 앱을 띄우기까지 해야 할 일들을 나열해봅니다.

① SSH로 서버에 접속합니다. AWS가 발급한 .pem 키 파일로 접속합니다.

  • ssh -i my-key.pem ubuntu@43.202.58.11

② JDK를 설치합니다. 서버에는 Java가 없습니다.

  • sudo apt update && sudo apt install -y openjdk-21-jdk
  • java -version으로 설치 확인

③ 로컬에서 JAR 파일을 빌드하고 서버로 전송합니다.

  • 로컬: ./gradlew build
  • scp -i my-key.pem build/libs/app.jar ubuntu@43.202.58.11:/home/ubuntu/

④ 서버에서 앱을 실행합니다.

  • java -jar /home/ubuntu/app.jar

여기까지만 해도 8080 포트에서 앱이 뜹니다. 그런데 아직 외부에서 접근이 안 됩니다.

⑤ 보안그룹에서 포트를 엽니다. AWS 콘솔 → EC2 → 보안그룹 → 인바운드 규칙 편집 → 8080 포트 TCP 허용(또는 Nginx 설치 후 80/443). 이 단계를 빠트리는 것이 입문자가 가장 많이 겪는 상황입니다. 앱은 분명 실행 중인데 브라우저에서 접속이 안 됩니다. 보안그룹을 확인하세요.

⑥ SSH 세션이 끊어지면 앱도 죽습니다. 터미널을 닫으면 프로세스가 종료됩니다. 서버를 재시작하면 앱이 자동으로 뜨지 않습니다. 이것을 해결하는 것이 systemd입니다. systemd는 Linux의 프로세스 관리자입니다. 서비스 파일(/etc/systemd/system/myapp.service)을 작성하면 서버 재부팅 시 자동으로 앱이 실행됩니다.

  • sudo systemctl enable myapp — 부팅 시 자동 시작 등록
  • sudo systemctl start myapp — 지금 당장 시작
  • sudo systemctl status myapp — 상태 확인

여기서 잠깐 멈추고 돌아봅시다. 지금까지 한 일들을 세어보면: SSH 접속, JDK 설치, JAR 빌드, 파일 전송(scp), 보안그룹 설정, systemd 서비스 파일 작성, 서비스 등록. 코드 한 줄도 바꾸지 않았는데 해야 할 작업이 이렇게 많습니다. 이 고통을 의도적으로 느껴두세요. 앞으로 소개할 플랫폼들이 이 중 얼마나 많은 것을 대신해주는지 비교해볼 기준점이 됩니다.

이 일곱 단계를 아래 시뮬레이터에서 직접 실행해보세요. 다음 단계 ▶ 를 누를 때마다 빈 우분투 한 대가 외부에서 접속 가능한 상시 서버가 되어 갑니다. JAR 파일이 노트북에서 서버로 건너가는 순간, 실행은 됐는데 보안그룹에 막혀 접속이 안 되는 순간, 그리고 재부팅 후 systemd가 앱을 살려내는 순간까지 — 전부 데이터가 움직이는 흐름으로 볼 수 있습니다.

EC2 수동 배포 시뮬레이터 — 일곱 단계 모두 사람 손으로 한다는 점에 주목
흔한 실수 환경 변수(DB 비밀번호, API 키 등)를 application.properties에 하드코딩한 채로 JAR을 만들고 서버에 올리는 경우가 있습니다. 비밀값은 절대 소스 코드나 JAR 파일 안에 넣지 마세요. 서버에서는 환경 변수(export DB_PASSWORD=xxx)나 별도의 설정 파일로 주입해야 합니다. GitHub에 올라간 비밀값은 되돌릴 수 없습니다.

2단계 — Railway: git push 하면 끝

이제 같은 app.jar을 완전히 다른 방식으로 올려봅시다. Railway(railway.app)에 GitHub 저장소를 연결합니다. 거의 전부입니다. 이제 git push를 하면 Railway가 자동으로 코드를 감지하고, Gradle 빌드를 실행하고, JAR을 만들고, 컨테이너에 패키징하고, 서버에 배포하고, HTTPS 도메인까지 만들어줍니다.

아까 EC2에서 했던 일들을 다시 떠올려보세요: SSH, JDK 설치, scp, 보안그룹, systemd. Railway는 이것들을 모두 대신해줍니다. 개발자는 코드에만 집중하면 됩니다. 아래 시뮬레이터에서 git push ▶ 를 눌러보세요 — 방금 EC2에서 일곱 단계였던 그 배포가, 버튼 하나로 끝나는 것을 직접 확인할 수 있습니다.

Railway 시뮬레이터 — git push 한 번이면 감지·빌드·컨테이너화·배포·HTTPS가 전부 자동

Railway가 대신 해주는 일들을 나열하면:

  • 서버 인프라 프로비저닝(EC2 만들기 같은 것)
  • 빌드 환경 구성(JDK, Gradle 실행)
  • 컨테이너 이미지 빌드
  • 배포 및 롤아웃
  • HTTPS 인증서 발급·갱신
  • 프로세스 재시작(앱이 죽으면 자동으로 다시 띄움)

이 편리함의 대가는 무엇일까요? 제어권입니다. 서버 사양을 세밀하게 조정하기 어렵고, 특수한 네트워크 구성이나 보안 정책을 적용하기 어렵습니다. 무료 플랜에는 사용량 제한이 있습니다. 대규모 서비스나 특수한 요구사항이 있는 엔터프라이즈 환경에는 맞지 않을 수 있습니다. 하지만 작은 팀의 사이드 프로젝트나, 아직 사용자가 많지 않은 초기 서비스라면 Railway(또는 Render, Fly.io 같은 유사 PaaS)는 탁월한 선택입니다.

한 줄 정리 PaaS(Platform as a Service)는 인프라 관리를 플랫폼에 위임하는 모델입니다. EC2에서 직접 했던 작업들을 플랫폼이 자동화해줍니다. "취미 프로젝트는 PaaS, 회사 서비스는 클라우드"라는 말이 있을 만큼, 규모에 따라 적합한 도구가 다릅니다.

3단계 — EKS(Kubernetes): 컨테이너가 50개라면

Railway로 올린 앱이 잘 돌고 있습니다. 그런데 팀이 커지고 서비스가 성장하면서 상황이 달라집니다. 마이크로서비스로 아키텍처가 분리되면서 배포해야 할 서비스가 10개, 20개, 50개가 됩니다. 각 서비스마다 인스턴스를 여러 개 띄워서 트래픽을 분산해야 합니다. 서비스 하나가 죽으면 자동으로 재시작되어야 합니다. 새 버전을 배포할 때 서비스 중단 없이 롤링 업데이트가 되어야 합니다.

이런 요구사항들을 수작업으로 관리하는 것은 불가능합니다. 이것이 컨테이너 오케스트레이션(container orchestration)이 등장한 이유이고, 그 표준이 Kubernetes(k8s)입니다. AWS에서 관리형 Kubernetes를 제공하는 서비스가 EKS(Elastic Kubernetes Service)입니다.

Kubernetes의 핵심 개념을 간략히 소개합니다:

  • Pod: 컨테이너 하나(또는 묶음)의 실행 단위. 우리 JAR가 컨테이너로 패키징되어 Pod 안에서 실행됩니다.
  • Deployment: "이 Pod를 3개 복사해서 항상 3개가 살아 있게 유지해"라는 선언. 하나가 죽으면 자동으로 새 Pod를 띄웁니다.
  • Service: Pod들을 하나의 주소로 묶어주는 로드밸런서. Pod가 몇 개든 클라이언트는 단일 주소로 접근합니다.

단, 솔직히 말씀드립니다: 입문 팀에게 Kubernetes는 보통 과잉입니다. 설정 파일만 수십 개, 개념만 수십 가지입니다. 사용자가 수천 명도 안 되는 초기 서비스에 EKS를 도입하면 인프라 운영에만 시간이 다 빠져나갑니다. 스타트업 팀이라면 Railway나 Render로 시작하고, 트래픽이 진짜 문제가 되는 시점에 Kubernetes를 검토하는 것이 현실적인 선택입니다. 지금 EKS를 배우는 이유는 "언제 이것이 필요해지는가"를 이해하기 위해서입니다.

4단계 — GitOps와 ArgoCD: 선언의 힘

Kubernetes를 쓰고 있다면 이런 상황을 상상해보세요. 새 버전을 배포하려면 kubectl apply -f deployment.yaml을 직접 실행해야 합니다. 여러 명이 배포 권한을 가지고 있어서 누가 언제 어떤 버전을 배포했는지 추적이 어렵습니다. 실수로 잘못된 설정이 클러스터에 들어가도 알기 어렵습니다.

GitOps는 이 문제를 해결하는 운영 방식입니다. 핵심 아이디어: Git 저장소가 클러스터의 원하는 상태(desired state)를 정의합니다. Git에 YAML 파일을 커밋하면 ArgoCD라는 에이전트가 이것을 감지하고, 실제 클러스터를 그 상태에 맞추어 계속 동기화합니다. 배포는 더 이상 "명령"이 아니라 "선언"이 됩니다.

GitOps의 장점은 여럿입니다. 모든 배포 변경이 Git 커밋 히스토리에 기록됩니다. 잘못된 배포를 롤백하려면 Git에서 이전 커밋으로 revert하면 됩니다. 클러스터 상태가 Git과 달라지면 ArgoCD가 자동으로 수정합니다(누군가 직접 클러스터를 수정했더라도 원래 상태로 돌아옵니다). 감사 로그가 자동으로 남습니다.

짚고 가기 2단계에서 소개한 Railway를 기억하시나요? GitHub에 push하면 자동으로 배포가 됩니다. 사실 이것이 아기 GitOps였습니다. Git이 원하는 상태(코드)를 정의하고, 플랫폼이 클러스터(서버)를 그 상태에 맞추는 것 — GitOps의 본질입니다. Railway는 그것을 단순하게 구현한 것이고, ArgoCD는 그것을 Kubernetes 위에서 완전히 구현한 것입니다.

GitOps reconcile 루프 — 끝없는 동기화

ArgoCD의 동작 방식을 조금 더 들여다봅니다. ArgoCD는 주기적으로(보통 3분마다) Git 저장소를 확인합니다. 저장소의 YAML과 실제 클러스터 상태를 비교합니다. 차이가 있으면 클러스터를 Git의 상태에 맞게 수정합니다. 이 사이클을 reconcile 루프(화해 루프)라고 부릅니다. "원하는 상태"와 "실제 상태"를 끝없이 일치시키려는 루프입니다.

이 다이어그램이 보여주는 것은 단순히 "자동 배포"가 아닙니다. 인프라의 진실(source of truth)이 Git으로 이동했다는 것입니다. 클러스터에 무슨 일이 일어났는지 알고 싶으면 클러스터를 뒤지는 것이 아니라 Git 히스토리를 봅니다. 이것이 현대 인프라 운영의 방향입니다.

한 줄 정리 자동화 사다리: EC2(모든 것을 내가) → PaaS/Railway(인프라는 위임) → Kubernetes(오케스트레이션) → GitOps/ArgoCD(Git이 진실의 원천). 올라갈수록 편하지만, 내부를 이해하고 선택하는 것이 중요하다. 입문 팀에게는 Railway가, 규모가 커지면 EKS+GitOps가 적절하다.

3부 도메인 + HTTPS

2부에서 EC2 서버를 띄우고 나면 뿌듯한 감정과 함께 이런 생각이 듭니다. "이제 됐다! 근데… 주소가 http://43.202.58.11:8080이라고?" 공인 IP 주소로 접근하는 것은 기술적으로는 동작하지만, 실제 서비스라고 부르기에는 부족합니다. 사용자에게 IP 주소를 알려줄 수도 없고, 앱 스토어는 평문 HTTP 통신을 기본으로 차단하고, 브라우저는 빨간 경고를 띄웁니다. 도메인 이름과 HTTPS는 배포의 마무리가 아니라, 서비스를 서비스답게 만드는 기본값입니다. 이 부에서는 그 두 가지를 어떻게 붙이는지, 왜 그렇게 동작하는지를 따라갑니다.

DNS A레코드 — IP를 사람의 언어로

DNS(Domain Name System)가 무엇을 하는지는 1부에서 간략히 소개했습니다. 이번에는 실제로 어떻게 설정하는지까지 들어가봅니다. 도메인을 구매한다는 것은 "이 이름에 대한 관리 권한"을 사는 것입니다. 가비아(gabia.com), AWS Route 53, 클라우드플레어 같은 도메인 등록대행사(registrar)에서 1년 단위로 구입할 수 있습니다. 짧고 기억하기 쉬운 .com 도메인은 연간 1~2만 원 수준입니다.

도메인을 구매한 후 해야 할 일은 단순합니다. DNS 관리 패널에서 A 레코드(Address Record)를 추가합니다. A 레코드는 "이 도메인 이름을 이 IPv4 주소로 연결하라"는 지시 한 줄입니다. 예를 들어 api.myapp.com을 EC2 공인 IP 43.202.58.11로 연결하고 싶다면 아래처럼 설정합니다.

  • 이름(Name): api (호스트명. 루트 도메인에 붙이려면 @)
  • 타입(Type): A
  • 값(Value): 43.202.58.11
  • TTL: 300 (초 단위 캐시 유지 시간. 처음에는 짧게, 안정되면 길게)

설정을 저장한다고 즉시 반영되지는 않습니다. DNS 정보는 전 세계에 분산된 수천 개의 네임서버에 캐시되어 있어서, 변경 사항이 완전히 전파(propagation)되기까지 수 분에서 최대 48시간이 걸릴 수 있습니다. 대부분의 경우 수 분 안에 되지만, "설정했는데 왜 안 되죠?"라는 질문의 절반은 DNS 전파를 기다리지 않아서입니다. nslookup api.myapp.com 또는 dig api.myapp.com 명령으로 현재 조회되는 IP를 확인할 수 있습니다.

AWS Route 53을 쓰는 경우라면 EC2와 같은 계정 안에서 관리할 수 있어서 편리합니다. Route 53은 단순 A 레코드 외에도 Alias 레코드를 지원하는데, 이것은 ELB(로드밸런서)나 CloudFront 같은 AWS 리소스에 직접 연결할 때 쓰입니다. IP가 바뀌어도 Alias가 자동으로 따라가기 때문에 EC2 재시작 시 IP 변경 문제를 우회할 수 있습니다. Elastic IP를 할당하는 방법과 함께 알아두면 좋습니다.

흔한 실수 EC2를 중지(stop)했다가 다시 시작(start)하면 공인 IP가 바뀝니다. DNS A 레코드에 이 IP가 박혀 있다면, 재시작 후 모든 요청이 엉뚱한 곳으로 가거나 응답 없음이 됩니다. 해결책은 둘 중 하나입니다: Elastic IP를 인스턴스에 붙여 고정 IP를 확보하거나, 처음부터 Route 53 Alias + ALB 조합으로 IP에 의존하지 않는 구조를 만드세요.

리버스 프록시 — Nginx가 현관문을 지키는 이유

도메인을 연결했습니다. 이제 브라우저에서 http://api.myapp.com을 치면 서버에 닿습니다. 그런데 Spring Boot는 8080 포트에서 듣고 있습니다. 브라우저는 HTTP라면 80번 포트로 기본 요청을 보냅니다. 이 불일치를 어떻게 해결할까요?

방법 하나는 Spring Boot를 80번 포트에서 실행하는 것입니다. 하지만 Linux에서 1024 미만의 포트는 root 권한이 필요하고, 하나의 서버에서 여러 앱을 운영할 때는 포트가 충돌합니다. 그래서 실무에서는 Nginx를 현관문으로 세웁니다. Nginx는 80포트(HTTP)와 443포트(HTTPS)에서 요청을 받고, 내부의 Spring Boot가 듣고 있는 8080 포트로 요청을 넘겨줍니다. 이것이 리버스 프록시(reverse proxy)입니다.

Nginx 설정 파일(/etc/nginx/sites-available/myapp)은 개념적으로 이렇게 생겼습니다:

  • server { listen 80; server_name api.myapp.com; … } — 80포트에서 이 도메인을 담당
  • location / { proxy_pass http://localhost:8080; } — 모든 요청을 내부 8080으로 전달

리버스 프록시가 주는 혜택은 이것만이 아닙니다. 하나의 IP와 서버에서 여러 도메인을 운영하고 싶다면 Nginx의 server_name을 다르게 설정한 블록을 여러 개 만들면 됩니다. api.myapp.com은 8080으로, admin.myapp.com은 8081로 분기하는 것입니다. 또한 TLS 암호화를 Nginx 레벨에서 처리하면 Spring Boot는 내부 HTTP 통신만 신경 쓰면 됩니다. 요청 속도 제한(rate limiting)으로 과도한 요청을 막거나, 정적 파일(.html, .css, 이미지)을 Spring Boot를 거치지 않고 Nginx가 직접 서빙하는 설정도 여기서 합니다. Nginx는 "서버 앞의 똑똑한 관리인"이라고 기억하면 됩니다.

짚고 가기 Nginx는 보안그룹과 Spring Boot 사이에 위치합니다. 외부에서 보안그룹은 80/443 포트만 열고, 8080은 닫아도 됩니다. Spring Boot 포트가 외부에 직접 노출되지 않으니 그만큼 공격 표면이 줄어듭니다. 1부의 요청 여정 지도에서 Nginx가 화살표 중간에 있는 이유가 바로 이것입니다.

HTTPS — 자물쇠는 선택이 아니라 기본

도메인도 붙었고 Nginx도 올렸습니다. 그런데 아직 http:// 입니다. 주소창에 "주의 요함"이라고 뜨고, iOS 앱에서는 연결 자체가 막히기도 합니다. HTTPS로 업그레이드해야 합니다.

HTTPS(HTTP Secure)는 HTTP 통신에 TLS(Transport Layer Security) 암호화를 씌운 것입니다. TLS가 하는 일은 두 가지입니다. 첫째, 신원 확인: "이 서버가 정말 api.myapp.com인가?"를 공신력 있는 기관(CA, Certificate Authority)이 발급한 인증서로 증명합니다. 둘째, 암호화: 클라이언트와 서버 사이를 오가는 모든 데이터를 암호화해서 중간에서 도청하거나 변조할 수 없게 합니다. 로그인 정보, 결제 데이터, 개인 정보가 평문으로 오가는 것을 막는 최소한의 안전장치입니다.

TLS 인증서를 어떻게 구할까요? 두 가지 현실적인 옵션이 있습니다.

Let's Encrypt는 비영리 CA로, 무료로 인증서를 발급해줍니다. EC2나 자체 서버를 쓴다면 certbot 도구로 Nginx와 연동하면 됩니다. sudo certbot --nginx -d api.myapp.com 명령 하나로 인증서를 발급받고 Nginx 설정까지 자동으로 수정해줍니다. 인증서 유효기간은 90일이지만, certbot이 자동 갱신 크론 작업을 설정해주므로 신경 쓸 필요가 없습니다. 연간 비용: 0원.

AWS ACM(Certificate Manager)은 AWS 인프라 안에서 쓸 때의 선택지입니다. ALB(Application Load Balancer)나 CloudFront에 붙이는 인증서는 ACM에서 발급받아 연결하는 것이 가장 편리합니다. 역시 무료이고 자동 갱신됩니다. 단, ACM 인증서는 EC2에 직접 설치하는 방식으로는 쓸 수 없습니다(ALB나 CloudFront를 통해서만 사용 가능). EC2 + Nginx 조합이라면 Let's Encrypt, ALB를 앞에 세우는 구조라면 ACM이 자연스러운 선택입니다.

흔한 실수 Flutter 앱에서 http:// 주소를 그대로 두고 iOS 빌드를 했다가 앱에서 네트워크 요청이 아예 안 되는 경우가 있습니다. iOS의 ATS(App Transport Security) 정책은 기본적으로 평문 HTTP 요청을 차단합니다. 예외 설정을 추가할 수는 있지만, 앱 스토어 심사에서 그 이유를 소명해야 합니다. Android 역시 API 28부터 평문 HTTP를 기본 차단합니다. 처음부터 HTTPS로 서버를 세우는 것이 가장 간단한 해결책입니다.

인증서를 발급받고 Nginx에 연결하면 설정이 자동으로 업데이트됩니다. 이제 http://로 접근해도 Nginx가 https://로 자동 리다이렉트(301 redirect)하도록 설정할 수 있습니다. 사용자는 의식하지 않아도 항상 암호화된 연결을 사용하게 됩니다. 주소창에 자물쇠가 뜨고, "주의 요함" 경고가 사라집니다.

1부에서 배운 지도를 다시 떠올려보세요. 사용자 스마트폰 → DNS → 공인IP → 보안그룹 → Nginx → JAR:8080 → DB. 이 부에서 우리는 DNS(A 레코드 등록)와 Nginx(리버스 프록시 + TLS 처리) 구간을 채웠습니다. 화살표 두 개가 완성되었습니다.

한 줄 정리 도메인 A레코드로 IP를 이름으로 감추고, Nginx 리버스 프록시로 80/443을 내부 8080에 연결하고, Let's Encrypt(자체 서버) 또는 ACM(AWS ALB)으로 TLS 인증서를 붙인다. HTTPS는 선택이 아니라 기본 — 앱 스토어와 브라우저 모두 평문 HTTP를 막는다.

4부 Flutter 앱 배포

백엔드 서버를 배포하고 나면 자연스럽게 다음 질문이 생깁니다. "그럼 Flutter 앱은 어떻게 배포하지?" 그런데 앱 배포를 처음 시도하는 분들이 가장 먼저 맞닥뜨리는 벽은 기술적인 것이 아니라 멘탈모델의 차이입니다. 백엔드 배포는 "내 JAR을 서버에 올린다"는 그림입니다. 반면 앱 배포는 "내 앱이 Google/Apple의 심사를 통과해서 스토어에 실린다"는 그림입니다. 서버가 없습니다. 직접 올릴 곳이 없습니다. 심사관이 있고, 트랙이 있고, 출시 프로세스가 있습니다. 이 차이를 먼저 머릿속에 세팅하는 것이 4부의 출발점입니다.

빌드 산출물 — APK, AAB, IPA의 정체

Spring Boot가 app.jar을 만들듯, Flutter도 빌드하면 플랫폼별 산출물이 생깁니다. 각 파일 형식은 역할이 다릅니다.

APK(Android Package Kit)는 안드로이드 앱을 하나의 파일로 묶은 것입니다. 우리가 인터넷에서 "myapp.apk 다운로드해서 설치하세요"로 배포할 때 쓰는 바로 그 파일입니다. 직접 설치(사이드로딩)가 가능하고, Firebase App Distribution 같은 도구로 테스터에게 배포할 때 편리합니다. Flutter 명령: flutter build apk.

AAB(Android App Bundle)는 Google Play 스토어 전용 형식입니다. APK와 달리 모든 기기 아키텍처·해상도·언어에 해당하는 리소스를 전부 담고 있으며, Play 스토어가 각 기기에 맞는 최적화된 APK를 자동으로 생성·배포합니다. 결과적으로 사용자가 다운로드하는 앱 크기가 줄어듭니다. 2021년부터 Google Play는 새 앱 제출 시 AAB를 기본 요구합니다. Flutter 명령: flutter build appbundle.

IPA(iOS App Archive)는 iOS 앱의 패키지 형식입니다. Xcode가 빌드하고 서명한 결과물로, App Store Connect에 제출하거나 TestFlight에 올릴 때 씁니다. Flutter로 IPA를 만들려면 macOS 기기와 Xcode가 필요합니다. Windows나 Linux에서는 iOS 앱을 직접 빌드할 수 없습니다. Flutter 명령: flutter build ipa (또는 Xcode 아카이브 메뉴).

빌드 산출물에는 두 가지 모드가 있습니다. 디버그(debug) 빌드는 개발 중에 핫 리로드, 디버거 연결, 성능 오버레이 등 개발 편의 기능이 켜져 있는 대신 크기가 크고 느립니다. 절대 스토어에 제출해서는 안 됩니다. 릴리스(release) 빌드는 모든 디버그 코드가 제거되고 최적화·난독화가 적용된 버전입니다. 스토어 제출, 테스터 배포 모두 반드시 릴리스 빌드를 사용해야 합니다. flutter build apk --release처럼 --release 플래그를 붙이거나, AAB/IPA는 기본이 릴리스입니다.

흔한 실수 디버그 APK를 테스터에게 보냈더니 "앱이 너무 느리다", "용량이 너무 크다"는 피드백이 왔습니다. 디버그 빌드는 실제 성능과 크기를 반영하지 않습니다. 내부 테스트를 위한 배포도 반드시 릴리스 빌드를 사용하세요. 또한 flutter run으로 실행하는 것은 디버그 모드입니다 — 릴리스 모드로 실행하려면 flutter run --release를 쓰세요.

코드 서명 — 위변조를 막는 도장

릴리스 빌드를 만들었다고 끝이 아닙니다. 스토어에 제출하기 전에 반드시 코드 서명(code signing)을 거쳐야 합니다. 코드 서명이란 무엇일까요? 인감 도장을 생각해보세요. 공식 서류에 인감 도장을 찍으면 "이것은 진짜 내가 작성하고 인정한 문서"임을 증명합니다. 코드 서명은 앱에 찍는 디지털 인감 도장입니다. "이 앱은 정말 이 개발자가 만든 것이고, 배포 이후 변조되지 않았음"을 보장합니다.

안드로이드: Keystore 파일. 개발자가 직접 .jks 또는 .keystore 파일을 생성합니다. 이 파일 안에 암호화 키가 들어 있습니다. 릴리스 빌드 시 이 키로 APK/AAB에 서명합니다. 서명에 쓴 키가 바뀌면 Play 스토어는 "다른 앱"으로 인식하고 업데이트를 거부합니다. Keystore 파일을 분실하면 기존 앱을 업데이트할 수 없게 됩니다. 절대 잃어버리지 마세요. Google Drive, 비밀번호 관리 도구 등 안전한 곳에 보관하고, 비밀번호도 함께 기록해두세요.

iOS: 인증서(Certificate) + 프로비저닝 프로파일(Provisioning Profile). Apple의 코드 서명 체계는 안드로이드보다 복잡합니다. Apple Developer Program($99/년)에 등록해야 하고, Apple이 발급하는 배포용 인증서(Distribution Certificate)와, 어떤 앱·기기에서 실행 가능한지 권한을 정의하는 프로비저닝 프로파일이 함께 필요합니다. Xcode가 대부분 자동으로 처리해주지만, 팀 개발 환경에서 서명 설정이 어긋나면 빌드가 실패합니다. "No signing certificate" 오류는 iOS 앱 개발자라면 누구나 한 번쯤 만나는 고통입니다.

짚고 가기 코드 서명 키(안드로이드 Keystore, iOS 인증서)는 앱의 신원 증명입니다. 잃어버리면 기존 앱을 업데이트할 권한을 잃습니다. GitHub 공개 저장소에 절대 올리지 말고, 팀 전용 비밀 관리 도구나 암호화된 저장소에 보관하세요. 환경 변수 비밀값과 마찬가지로, 코드 서명 키 유출은 되돌리기 매우 어렵습니다.

배포 트랙 3단 — 내부 테스트에서 전 세계 출시까지

앱을 빌드하고 서명까지 마쳤습니다. 바로 전 세계에 출시할까요? 보통은 아닙니다. 실제 배포는 단계적으로 이루어집니다. 소수의 테스터에게 먼저 배포해서 버그를 잡고, 범위를 넓혀가다가 최종적으로 모든 사용자에게 공개합니다. 이것이 배포 트랙(deployment track)의 개념입니다.

1단: 내부 테스트(Internal Testing). 가장 빠르고 제한적인 트랙입니다. 개발팀 내부 및 지정된 소수 테스터들이 대상입니다. Android에서는 Play Console의 "내부 테스트" 트랙에 APK/AAB를 올리면 심사 없이 몇 분 안에 테스터가 설치할 수 있습니다. iOS에서는 TestFlight의 "내부 테스터(Internal Tester, 최대 100명)"가 동일한 역할을 합니다. Firebase App Distribution은 Android·iOS 모두에서 쓸 수 있는 서드파티 대안으로, 스토어 계정 없이 이메일로 테스터를 초대해서 APK/IPA를 배포할 수 있습니다. 학교 팀 프로젝트나 사내 검토 단계에서 매우 유용합니다.

2단: 비공개 출시(Closed/Open Beta). 내부 테스트를 통과한 후, 더 넓은 범위의 베타 테스터에게 공개합니다. Google Play의 "비공개 테스트(Alpha)", "공개 테스트(Beta)" 트랙, TestFlight의 외부 테스터(External Tester, 최대 10,000명)가 여기에 해당합니다. 이 단계부터는 Apple의 경우 TestFlight 심사(보통 1~2일)가 있습니다. 테스터 피드백을 반영하고 충분히 안정화된 후에 다음 단계로 넘어갑니다.

3단: 프로덕션(Production). 앱 스토어에 정식 출시됩니다. 모든 사용자가 검색하고 설치할 수 있게 됩니다. Android(Google Play)는 심사 기간이 보통 며칠 이내이지만, 정책 위반 여부에 따라 길어질 수 있습니다. iOS(App Store)는 Apple 심사가 필수이며, 일반적으로 24~48시간이지만 주말이나 대규모 업데이트 시즌에는 더 걸리기도 합니다. 심사를 한 번 통과해도, 다음 버전 업데이트마다 다시 심사를 받아야 합니다.

스토어 심사 — 흔한 반려 이유

프로덕션 트랙에 제출했는데 반려(reject)가 왔습니다. 특히 Apple에서 자주 겪는 상황입니다. 반려를 받으면 수정 후 재제출해야 하고, 또 심사 대기 시간이 발생합니다. 흔한 반려 이유를 미리 알아두면 첫 제출부터 통과 확률이 높아집니다.

  • 권한 사용 설명 누락: 카메라, 위치, 마이크, 연락처 등을 사용하면 Info.plist에 사용 목적을 설명하는 문자열(NSCameraUsageDescription 등)이 반드시 있어야 합니다. "카메라에 접근합니다"처럼 모호한 설명이 아니라, 실제 앱에서 왜 필요한지 구체적으로 적어야 합니다.
  • 개인정보 처리방침(Privacy Policy) URL 누락: 사용자 데이터를 수집·처리하는 앱이라면 접근 가능한 개인정보 처리방침 URL이 있어야 합니다. 간단한 정적 페이지라도 만들어 링크를 제공하세요.
  • 테스트 계정 미제공: 로그인이 필요한 기능이 있으면 심사관이 테스트할 수 있는 데모 계정(아이디/비밀번호)을 제출 노트에 적어야 합니다.
  • 앱 설명과 실제 기능 불일치: 스크린샷이나 설명에 없는 기능을 앱이 요구하거나, 스크린샷이 실제 앱과 다르면 반려됩니다.
  • 평문 HTTP 사용: 앞서 언급한 ATS 정책. HTTPS로 통신해야 합니다.

핵심 연결 고리 — baseURL 스위치

이제 가장 중요한 순간입니다. 2부에서 서버를 올렸고, 3부에서 도메인과 HTTPS를 붙였습니다. 4부의 Flutter 앱이 그 서버와 통신하려면 앱 안에 서버 주소를 넣어야 합니다. 이것이 baseURL입니다.

Flutter 프로젝트에서 일반적으로 다음과 같은 패턴을 씁니다. 개발 중에는 로컬 서버 주소를 쓰고, 프로덕션 빌드에서는 실제 서버 주소를 씁니다:

  • 개발(dev): const baseURL = 'http://localhost:8080';
  • 프로덕션(prod): const baseURL = 'https://api.myapp.com';

이 스위치를 어디서, 어떻게 바꿔끼울지는 5부에서 환경 분리와 함께 더 자세히 다룹니다. 여기서 핵심은 이것입니다: 2부에서 올린 백엔드 서버의 주소(3부에서 도메인+HTTPS로 완성된)가 바로 이 baseURL에 들어갑니다. 백엔드 배포와 앱 배포가 연결되는 지점입니다. 서버를 올리기 전까지 앱의 실제 프로덕션 baseURL을 확정할 수 없었던 이유가 여기 있습니다.

한 줄 정리 앱 배포는 "서버에 올리는" 것이 아니라 "빌드(APK·AAB·IPA)→서명(keystore·인증서)→트랙(내부테스트→비공개→프로덕션)→스토어 심사"의 파이프라인이다. 핵심 연결점은 앱의 baseURL — 2·3부에서 올린 백엔드 주소가 바로 여기에 들어온다.

5부 전체 잇기

여기까지 왔습니다. 0부에서 "내 컴에선 되는데"의 정체를 파악하고, 1부에서 요청의 여정 지도를 그렸고, 2부에서 JAR을 서버에 올리는 네 가지 방법을 경험했고, 3부에서 도메인과 HTTPS를 붙였고, 4부에서 Flutter 앱이 스토어에 도달하는 파이프라인을 따라갔습니다. 이제 이 모든 조각을 하나의 그림으로 잇겠습니다. 그리고 실무에서 반드시 맞닥뜨리게 되는 두 가지 주제 — 환경 분리와 비용 감각 — 를 함께 정리합니다.

환경 분리 — dev, staging, prod는 왜 다로 있는가

팀 프로젝트를 처음 시작할 때는 서버 하나, 데이터베이스 하나, 앱 하나면 충분해 보입니다. 그런데 서비스가 실제 사용자를 받기 시작하면 문제가 생깁니다. 새 기능을 개발하다가 버그가 있는 코드를 서버에 올렸더니 지금 사용 중인 사용자들도 오류를 겪습니다. 테스트 데이터를 실수로 실제 데이터베이스에 넣었습니다. 새 API 스펙을 개발 중인데 Flutter 앱이 아직 그 스펙을 따르지 않아서 기존 앱 사용자들의 API 호출이 깨집니다. 이 모든 문제의 원인은 하나입니다: 개발 중인 것과 운영 중인 것이 같은 환경을 공유하고 있기 때문입니다.

환경 분리는 이것을 막는 가장 기본적인 설계입니다. 일반적으로 세 가지 환경을 구분합니다.

  • dev(개발 환경): 개발자들이 새 기능을 개발하고 테스트하는 환경. 실험적인 코드, 더미 데이터, 잦은 재배포가 허용됩니다. 다운타임이 있어도 괜찮습니다.
  • staging(스테이징 환경): 프로덕션과 동일한 구성을 갖추되, 실제 사용자 데이터가 없는 환경. "이 버전을 실제로 올려도 괜찮은가?"를 마지막으로 검증하는 리허설 무대입니다. 팀 규모가 작으면 staging을 dev와 통합하기도 합니다.
  • prod(프로덕션 환경): 실제 사용자가 사용하는 환경. 안정성이 최우선이고, 변경은 충분히 테스트된 것만 올라와야 합니다.

이 세 환경을 분리하면 Flutter 앱의 baseURL도 환경에 따라 달라집니다. 개발 중에는 dev 서버 주소를 쓰고, 스토어 제출 빌드에는 prod 서버 주소를 씁니다. 4부에서 언급한 baseURL 스위치가 바로 이 환경 분리와 맞물립니다. 아래 분리도에서 각 환경의 baseURL이 어떻게 연결되는지 확인해보세요.

Flutter에서 환경을 나누는 가장 간단한 방법은 --dart-define 플래그를 활용하는 것입니다. flutter run --dart-define=ENV=dev처럼 빌드 시점에 환경 변수를 주입하면, 코드 안에서 const env = String.fromEnvironment('ENV')로 읽어 분기할 수 있습니다. 또는 lib/env/dev.dart, lib/env/prod.dart처럼 환경별 설정 파일을 두고 빌드 스크립트에서 복사하는 방식도 흔히 쓰입니다. 어떤 방식이든 핵심은 서버 주소, API 키 같은 환경별 값들이 코드 안에 하드코딩되지 않고, 빌드 시 또는 실행 시 주입된다는 것입니다.

비밀값 관리 — .env 파일은 Git에 올리지 않는다

환경 분리와 함께 반드시 다뤄야 할 것이 비밀값(secret) 관리입니다. 데이터베이스 비밀번호, API 키, JWT 시크릿 키, 서명 인증서 비밀번호 — 이것들은 절대 소스 코드에 들어가서는 안 됩니다. 소스 코드가 GitHub에 올라가는 순간, 공개 저장소라면 전 세계가, 비공개 저장소라도 접근 권한이 있는 모든 사람이 볼 수 있습니다.

서버에서 비밀값을 주입하는 기본적인 방법은 환경 변수입니다. export DB_PASSWORD=xxx처럼 서버의 셸 환경에 세팅하거나, systemd 서비스 파일에서 Environment="DB_PASSWORD=xxx"를 지정하거나, Railway/Render 같은 PaaS에서는 대시보드의 "Environment Variables" 패널에서 설정합니다. Spring Boot에서는 application.properties에 ${DB_PASSWORD}처럼 환경 변수를 참조하도록 작성하면 됩니다. Flutter 앱의 경우 API 키 같은 값은 앱 번들에 포함되면 역공학으로 추출될 수 있으므로, 민감한 로직은 백엔드 서버에서 처리하고 앱에는 최소한의 공개 가능한 값만 두는 것이 원칙입니다.

흔한 실수 .env 파일을 만들고 .gitignore에 추가했는데, 처음 한 번은 실수로 Git에 올려버렸습니다. git rm --cached .env로 제거해도 Git 히스토리에는 남아 있습니다. 비밀값이 한 번이라도 공개 저장소에 올라갔다면, 즉시 해당 키를 폐기하고 새로 발급받아야 합니다. 히스토리를 지우는 것만으로는 충분하지 않습니다 — 봇이 이미 크롤링했을 수 있습니다.

비용 감각 — 얼마나 들고, 어디서 시작할까

배포를 처음 배울 때 막연하게 "클라우드는 비싸다"거나 반대로 "다 무료 아닌가?"라고 생각하는 경우가 많습니다. 현실적인 비용 감각을 잡아봅시다.

AWS EC2 t2.micro / t3.micro는 프리티어(Free Tier) 대상 인스턴스입니다. AWS 신규 가입 후 12개월간, t2.micro는 월 750시간 무료입니다. 750시간은 한 달 내내(24×31=744시간) 인스턴스를 켜놓아도 남는 양입니다. 즉, 처음 1년은 서버 하나를 무료로 운영할 수 있습니다. 단, 데이터 전송 비용, EBS 스토리지(30GB까지 무료), RDS(별도 프리티어) 등도 함께 고려해야 합니다. 프리티어가 끝난 후 t2.micro는 온디맨드 기준 월 약 $8~9 정도입니다.

Railway의 무료 플랜(Hobby Free)은 월 $5 크레딧을 제공합니다. 소규모 프로젝트라면 이 안에서 운영이 가능합니다. 유료 Hobby 플랜은 월 $5이며 더 많은 자원과 24/7 가동을 지원합니다. Render의 무료 인스턴스는 15분 비활성 시 자동으로 슬립 상태가 되고, 요청이 오면 콜드 스타트(30~60초 지연)가 발생합니다. 개발·데모용으로는 괜찮지만 실제 서비스에는 유료 플랜이 필요합니다.

실무에서 자주 쓰이는 원칙이 있습니다: "취미 프로젝트는 PaaS, 회사 서비스는 클라우드(IaaS/managed)." 개인 포트폴리오, 해커톤 프로젝트, 팀 과제라면 Railway나 Render로 빠르게 올리고 운영 부담 없이 쓰세요. 실제 서비스를 운영하고 사용자가 늘어날수록, 세밀한 제어와 최적화가 필요해지면 AWS/GCP/Azure 위에서 직접 관리하는 방향으로 이동합니다. 지금 당장 EKS를 배울 필요는 없지만, 사다리의 전체 그림을 알고 있으면 필요한 시점에 올라갈 수 있습니다.

CI/CD — push 하면 알아서 배포된다

지금까지 배포는 "내가 직접 실행하는 것"이었습니다. 로컬에서 빌드하고, scp로 전송하거나, Railway에 push하거나. 그런데 팀이 여럿이고 배포가 잦아지면 이것도 번거로워집니다. 누군가 main 브랜치에 push했을 때 자동으로 빌드되고 테스트되고 서버에 배포까지 되면 어떨까요? 이것이 CI/CD(Continuous Integration / Continuous Delivery)입니다.

CI(지속적 통합)는 코드가 push될 때마다 자동으로 빌드하고 테스트하는 파이프라인입니다. 버그가 있는 코드가 main 브랜치에 합쳐지기 전에 테스트로 잡아냅니다. CD(지속적 배포)는 테스트를 통과한 코드를 자동으로 서버에 배포합니다. 두 단계가 연결되면, 개발자는 코드를 push하는 것만으로 전체 파이프라인이 돌아갑니다.

도구는 GitHub Actions가 가장 접근하기 쉽습니다. 저장소에 .github/workflows/deploy.yml 파일을 만들고, "main 브랜치에 push가 올 때마다 이 명령들을 실행해"라고 정의합니다. 예를 들어: Gradle 빌드 → JAR 파일 생성 → SSH로 서버에 접속 → 새 JAR 전송 → 서비스 재시작. 처음에는 복잡해 보이지만, 한 번 만들어두면 이후 모든 배포가 자동화됩니다. Railway는 GitHub 연결만 해도 이 CI/CD 파이프라인을 기본으로 제공합니다 — 2부에서 말했던 "git push 하나로 끝"이 바로 내장 CI/CD였던 것입니다.

짚고 가기 CI/CD를 처음 들으면 거창하게 느껴지지만, 본질은 간단합니다: "내가 손으로 반복하던 배포 절차를 자동화 스크립트로 옮긴 것." Railway의 자동 배포가 아기 CI/CD였듯, GitHub Actions의 워크플로우는 그 스크립트를 직접 제어할 수 있는 버전입니다.

마스터 지도 회수 — 화살표가 전부 채워졌다

이 책의 시작부터 1부에서 소개한 마스터 지도를 기억하시나요? Flutter앱 → DNS → 공인IP → 보안그룹 → Nginx → JAR:8080 → DB. 이제 그 각 화살표에 이름이 붙고 어떻게 만드는지까지 알게 되었습니다.

  • Flutter 앱의 baseURL: 4부에서 환경 분리와 함께 설정 (dev ↔ prod 스위치)
  • DNS: 3부에서 A 레코드로 도메인을 공인 IP에 연결
  • 공인 IP: 2부의 EC2 인스턴스 또는 Railway 도메인
  • 보안그룹: 2부에서 80/443 포트 열기, 8080은 내부로
  • Nginx: 3부에서 리버스 프록시 + TLS 처리
  • JAR:8080: 2부의 Spring Boot 프로세스, systemd로 항상 살아 있음
  • DB: 2부에서 RDS 또는 로컬 MySQL, 환경 변수로 접속 정보 주입

단 하나의 API 요청이 사용자 손끝에서 출발해 데이터베이스에 닿기까지, 이 일곱 단계를 거칩니다. 배포란 이 일곱 단계를 하나씩 손으로 조립하는 일이었습니다. 이제 그 조립이 무엇을 의미하는지 알고 있습니다.

다음 한 걸음 — 이번 주말에 할 일

이 책을 읽었다고 배포를 "안다"고 말할 수는 없습니다. 배포는 직접 해봐야만 내 것이 됩니다. 개념은 이해했지만 손이 기억하지 않으면, 실제 배포 앞에서 다시 막막해집니다. 그래서 숙제가 있습니다.

이번 주말, Railway에 프로젝트 하나를 올려보세요. Spring Boot 프로젝트가 있다면 GitHub에 올리고, Railway에서 GitHub 저장소를 연결하세요. 없다면 Spring Initializr에서 "Hello, World!"를 리턴하는 API 하나만 있는 프로젝트를 만들어 올려보세요. 목표는 https://yourapp.up.railway.app/hello가 브라우저에서 열리는 것입니다. 이것 하나가 이 책 전체를 이해하는 것보다 더 많은 것을 가르쳐 줄 것입니다.

거기서 한 걸음 더 나아갈 여유가 있다면: Railway 앱에 데이터베이스를 붙여보고, 환경 변수로 접속 정보를 주입해보세요. 그 다음에는 도메인을 사서 연결해보세요. 그 다음에는 Flutter 앱의 baseURL을 그 도메인으로 바꾼 릴리스 빌드를 만들어보세요. 한 번에 다 하려 하지 말고, 한 단계씩. 각 단계마다 이 책의 해당 부분으로 돌아오면 "아, 이게 그 얘기였구나"가 훨씬 구체적으로 느껴질 것입니다.

배포는 처음에는 낯설고 두려운 영역입니다. 하지만 몇 번 경험하고 나면, 생각보다 단순한 조립의 연속이었다는 것을 알게 됩니다. 그리고 어느 순간, "내 컴에선 되는데"가 아니라 "서버에서도 된다"를 당연하게 말할 수 있게 됩니다. 그 날이 멀지 않았습니다.

한 줄 정리 dev/staging/prod 환경 분리로 운영 안정성을 확보하고, 비밀값은 환경 변수로 주입하고, PaaS로 시작해서 필요할 때 클라우드로 이동하고, CI/CD로 배포를 자동화한다. 그리고 이번 주말에 일단 한 번 올려본다 — 경험이 곧 이해다.

본편 2부의 4칸을, 컨테이너·이미지 저장소까지 넣어 5레벨로 더 잘게 나눠봅니다.

레벨 1: JAR 파일을 서버에 올려 직접 실행        (2부 EC2 시뮬레이터의 그 7단계)
레벨 2: Docker 이미지로 만들어 실행            (실행 환경째로 포장)
레벨 3: ECS/Fargate 또는 Kubernetes로 컨테이너 운영
레벨 4: EKS로 AWS에서 Kubernetes 운영          (관리형 k8s)
레벨 5: GitOps로 Git commit만 하면 자동 배포    (Argo CD)

본편의 IaaS / PaaS / SaaS 비유와 음식 비유를 한 줄로 잇습니다.

JAR 배포      = 도시락 하나 들고 가서 먹기            (EC2 = 빈 원룸, IaaS)
Docker 배포   = 도시락 + 전자레인지 + 식기까지 세트로 포장
ECS 배포      = AWS가 도시락을 적당한 자리에서 실행
Kubernetes    = 대형 푸드코트 운영 시스템
EKS           = AWS가 관리해주는 푸드코트 운영 시스템   (관리형, 입주만)
GitOps        = 메뉴판(Git)만 바꾸면 주방이 자동으로 그대로 세팅

2부 자동화 사다리 시뮬레이터에서 본 그 역설이 여기서도 똑같습니다 — 올라갈수록 내 손은 비고, 대신 알아야 할 개념은 늘어납니다.

S1. Spring Boot를 '서버에 올린다'의 두 형태 — JAR vs Docker

본편 2-0에서 본 app.jar을 두 가지로 올릴 수 있습니다.

① JAR 배포 — 빌드 결과물(build/libs/app.jar)을 서버에서 직접 실행합니다.

./gradlew clean bootJar          # 결과물: build/libs/app.jar
java -jar app.jar                # 서버에서 실행 (java가 미리 깔려 있어야 함)

이해하기 쉽지만 서버에 Java가 미리 깔려 있어야 하고(EC2 시뮬레이터의 3단계 "JDK 설치"), 서버마다 환경 차이에 영향을 받습니다. 0부의 "내 컴에선 되는데"가 서버에서 재발하는 지점이 바로 여기예요.

② Docker 배포 — 앱과 실행 환경(java, OS 설정)을 하나의 이미지로 포장합니다.

JAR 배포    = 도시락만 포장          → 식당(서버)에 전자레인지(java)가 있어야 함
Docker 배포 = 도시락 + 전자레인지 + 먹는 방법까지 함께 포장 → 식당에 아무것도 없어도 됨
# Dockerfile
FROM eclipse-temurin:21-jdk
WORKDIR /app
COPY build/libs/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
./gradlew clean bootJar
docker build -t spring-api:1.0.0 .
docker run -p 8080:8080 spring-api:1.0.0     # 로컬 실행 테스트
한 줄 정리 Docker의 진짜 가치는 "내 PC·테스트 서버·EKS Node에서 완전히 똑같이 실행된다"는 보장입니다. JDK 버전·OS 패키지 차이로 깨지는 일이 사라집니다.

S2. ECR — 왜 필요한가 (내 이미지를 EKS가 가져가려면)

docker build로 만든 이미지는 처음엔 내 컴퓨터 안에만 있습니다. EKS는 내 노트북 안을 들여다볼 수 없습니다. EKS가 이미지를 가져가려면 접근 가능한 이미지 저장소가 있어야 하고, AWS에서는 보통 Amazon ECR(= Docker 이미지 창고)을 씁니다.

Spring Boot 코드
  ↓ ./gradlew clean bootJar
JAR 빌드
  ↓ docker build
Docker 이미지
  ↓ docker push          ← 여기서 이미지가 ECR로 올라간다
ECR에 이미지 push
  ↓
deployment.yaml 에 ECR 이미지 주소 작성
  ↓ kubectl apply         ← "이 ECR 이미지로 Pod 띄워라"라고 알려줄 뿐
EKS가 ECR 에서 이미지 pull
  ↓
Pod 실행
가장 흔한 오해 kubectl apply가 이미지를 ECR에 올린다? 아니다. ECR push(docker push)는 kubectl apply 전에 이미 끝나 있어야 합니다. kubectl apply는 "이 ECR 주소의 이미지를 써서 Pod를 실행하라"고 지시만 하는 단계입니다.

ECR에 올리는 4단계 (리전·계정 ID는 본인 것으로):

# 1) 빌드 (아직 내 PC에만 있음)
docker build -t spring-api:1.0.0 .

# 2) ECR 로그인
aws ecr get-login-password --region ap-northeast-2 \
  | docker login --username AWS --password-stdin \
    123456789012.dkr.ecr.ap-northeast-2.amazonaws.com

# 3) ECR 주소로 태그 변경
docker tag spring-api:1.0.0 \
  123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/spring-api:1.0.0

# 4) push
docker push \
  123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/spring-api:1.0.0

ECR 없이도 되나? 됩니다 — image:엔 어떤 저장소든 올 수 있습니다(예: image: nginx:latest는 Docker Hub에서 pull). 다만 내가 만든 Spring Boot 이미지는 Docker Hub에 기본으로 없으니 어딘가에는 올려야 합니다(ECR · Docker Hub · GitHub Container Registry · Harbor). AWS EKS 기준에선 IAM 권한 연동·pull·보안·비용 관리가 한곳에서 되는 ECR이 자연스럽습니다.

S3. Kubernetes 핵심 개념 6가지

처음엔 Spring Boot 서버 하나면 됩니다. 하지만 실무는 회원·주문·결제·알림·파일·관리자·AI… 서버가 늘어나고, 각각을 컨테이너로 만들면 곧바로 질문이 쏟아집니다 — "죽으면 누가 살리지? 3개로 늘리려면? 무중단 배포는? 비밀값은? 외부 접속은? 로그는?". 이걸 선언형으로 풀어주는 시스템이 Kubernetes입니다(2부 k8s 시뮬레이터에서 Pod 죽이기 → self-heal로 체감한 그것).

개념한 줄 정의비유
Pod컨테이너가 실제 실행되는 최소 단위직원 한 명의 작업 공간
DeploymentPod를 몇 개 유지할지 관리(원하는 상태)"직원 3명 상시 근무" 지시
Service바뀌는 Pod들 앞의 고정 내부 주소직원은 바뀌어도 그대로인 고객센터 번호
Ingress외부 HTTP/HTTPS를 내부 Service로 잇는 입구백화점 정문 + 안내 데스크
ConfigMap일반 설정값 저장소사내 게시판의 운영 안내
Secret민감 설정값 저장소금고 (단, 완전한 금고는 아님)
  • Deployment replicas: 3 → "Pod를 항상 3개 유지". 하나가 죽으면 쿠버네티스가 새로 띄웁니다 = self-healing(시뮬레이터에서 본 그 동작).
  • Service — Pod는 죽었다 살아나며 IP가 바뀝니다. 그 앞에 spring-api-service라는 고정 이름을 둬서 "어느 Pod로든" 연결합니다.
  • Ingress — https://api.example.com → Ingress → spring-api-service → Pods. 3부의 "리버스 프록시·도메인·HTTPS"가 쿠버네티스에선 Ingress(+ALB)로 구현됩니다.
흔한 실수 Kubernetes Secret은 기본적으로 base64 인코딩일 뿐 암호화 금고가 아닙니다. 운영에선 AWS Secrets Manager / Parameter Store / External Secrets Operator를 함께 씁니다.

S4. EKS — AWS 관리형 쿠버네티스

쿠버네티스를 직접 깔면 관리할 게 많습니다 — Control Plane·etcd·API Server·업그레이드·보안 패치·노드·네트워크 플러그인·인증/인가·로깅. EKS는 이 Control Plane을 AWS가 관리해 줍니다.

직접 운영 = 건물을 직접 짓고 전기·수도·보안까지 관리
EKS      = AWS가 관리하는 건물에 입주해서 서비스만 운영

EKS 기준 최종 백엔드 배포 구조 (3부의 DNS·HTTPS와 연결):

사용자
  ↓
https://api.example.com
  ↓
Route 53            (DNS — 3부)
  ↓
ACM HTTPS 인증서     (TLS — 3부)
  ↓
AWS ALB             (Application Load Balancer)
  ↓
Kubernetes Ingress
  ↓
Kubernetes Service
  ↓
Spring Boot Pods
  ↓
RDS                 (관리형 DB)

1부 마스터 지도(앱→DNS→IP→방화벽→Nginx→JAR→DB)가 EKS 세계에선 이렇게 확장됩니다. Nginx 자리에 ALB+Ingress, 서버 자리에 Pod 여러 개, DB 자리에 RDS. 그림은 커졌지만 화살표의 의미는 똑같습니다.

S5. 일반 Kubernetes 배포 흐름 (사람이 직접 kubectl apply)

Spring Boot 코드
  ↓ ./gradlew clean bootJar → docker build → docker push (ECR)
deployment.yaml 의 image 를 ECR 주소로 작성
  ↓
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
kubectl apply -f ingress.yaml
  ↓
EKS가 manifest 를 읽음 → Node가 ECR에서 pull → Pod 실행 → Service 연결 → Ingress/ALB가 외부 노출

사람이 직접 하는 일: 빌드 · 이미지 push · YAML 수정 · kubectl apply.

deployment.yaml — 가장 중요한 줄은 image:(= ECR 이미지 주소)입니다.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: spring-api
  namespace: prod
spec:
  replicas: 2
  selector:
    matchLabels:
      app: spring-api
  template:
    metadata:
      labels:
        app: spring-api
    spec:
      containers:
        - name: spring-api
          image: 123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/spring-api:1.0.0
          ports:
            - containerPort: 8080
          env:
            - name: SPRING_PROFILES_ACTIVE
              value: prod

service.yaml — 여러 Pod 앞에 고정 내부 주소를 만듭니다.

apiVersion: v1
kind: Service
metadata:
  name: spring-api-service
  namespace: prod
spec:
  selector:
    app: spring-api
  ports:
    - port: 80
      targetPort: 8080
  type: ClusterIP

ingress.yaml — 외부 요청을 내부 Service로 잇습니다(ALB 연동).

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: spring-api-ingress
  namespace: prod
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
spec:
  ingressClassName: alb
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: spring-api-service
                port:
                  number: 80

kubectl apply 한 줄이 클러스터 안에서 하는 일:

1. API Server가 Deployment 요청을 받음
2. Deployment Controller가 ReplicaSet 생성
3. ReplicaSet이 Pod 2개 생성 요청
4. 각 Node의 kubelet이 Pod 실행 준비
5. kubelet이 image 주소 확인
6. ECR에서 spring-api:1.0.0 이미지 pull
7. 컨테이너 실행
8. Pod Running

S6. Deployment는 GitOps가 아니다 — '선언'과 'GitOps'의 차이

여기서 가장 헷갈리는 매듭을 풉니다. Deployment ≠ GitOps.

  • Deployment = 쿠버네티스 리소스 종류(선언 파일).
  • GitOps = Deployment 같은 선언 파일을 Git에 두고, Argo CD 같은 도구가 Git 상태와 클러스터 상태를 계속 맞추는 운영 방식.

즉 deployment.yaml은 GitOps의 재료일 뿐, 그 자체가 GitOps는 아닙니다.

쿠버네티스는 원래부터 선언형입니다. replicas: 3은 "지금 당장 만들어!"라는 명령이 아니라 "항상 3개 떠 있어야 해"라는 원하는 상태 선언입니다. 쿠버네티스는 원하는 상태와 현재 상태를 비교해 맞춥니다(2개면 하나 더). 하지만 이것만으로는 GitOps가 아닙니다.

deployment.yaml 작성             → 그냥 쿠버네티스 선언 파일
deployment.yaml 을 GitHub에 올림  → YAML을 Git으로 버전관리(아직 GitOps 아님)
─────────────────────────────────────────────────────────
Git의 YAML  ──감시──▶  Argo CD  ──비교/동기화──▶  실제 EKS 상태
   = 이 구조가 되어야 비로소 GitOps
짚고 가기 GitOps의 핵심 한 줄 — "Git 저장소가 운영 환경의 정답이고, Argo CD가 그 정답에 맞춰 클러스터를 계속 고친다."

S7. GitOps 배포 흐름 + 저장소 분리

개발자 코드 수정
  ↓ git push (App Repo)
GitHub Actions 실행
  ↓ bootJar → docker build → docker push (ECR, 태그=커밋해시)
Manifest Repo의 deployment.yaml image 태그 자동 수정 → git commit/push
  ↓
Argo CD가 Manifest Repo 변경 감지 → EKS에 sync
  ↓ EKS가 ECR에서 새 이미지 pull → Pod 교체

사람이 직접 하는 일은 단 하나 — 코드 수정 후 git push. 빌드·이미지 push·YAML 태그 수정·EKS 반영은 전부 자동입니다.

왜 저장소를 둘로 나누나 — 코드 이력과 배포 이력을 분리하고 권한도 따로 주기 위해서입니다.

spring-api-repo            (App Repo)      ── Spring Boot 소스 + Dockerfile + CI(.github/workflows)
spring-api-manifest-repo   (Manifest Repo) ── deployment/service/ingress.yaml 만   ← Argo CD가 보는 곳

이 전체 흐름을 아래 통합 시뮬레이터에서 직접 실행해보세요. 코드 수정 & git push ▶ 를 누르면 커밋이 App Repo → GitHub Actions(테스트 → 빌드) → ECR 저장 → Manifest Repo 갱신(GitOps 상태) → Argo CD 감지 → EKS Pod 롤링 교체까지 한 번에 흘러갑니다. 배포가 끝난 뒤에는 Pod 죽이기 💥(쿠버네티스 자체의 self-healing)와 kubectl로 몰래 변경 🔧(Argo CD의 selfHeal — Git이 정답)을 비교해보세요. 둘의 차이를 구분할 수 있다면 S3와 S8을 제대로 이해한 것입니다.

EKS + GitOps 통합 시뮬레이터 — 위 행은 CI(GitHub Actions), 아래 행은 CD(Argo CD)

S8. Argo CD — Git을 정답으로 삼는 감리자

Argo CD는 쿠버네티스용 GitOps 도구입니다. Git 저장소를 계속 바라보다가 Git에 적힌 상태 ≠ 실제 클러스터 상태면 Git 쪽으로 맞춥니다.

Git Repository ──▶ Argo CD ──▶ Kubernetes Cluster
예) Git: replicas 3 / image 1.0.1   vs   EKS: replicas 2 / image 1.0.0
    → Argo CD가 차이를 감지 → EKS를 replicas 3 / image 1.0.1 로 맞춤

GitOps의 핵심 파일은 Deployment보다 Argo CD의 Application 리소스입니다.

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: spring-api-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/your-org/spring-api-manifest-repo.git
    targetRevision: main
    path: apps/spring-api/prod          # ← 이 폴더가 운영 배포의 '정답'
  destination:
    server: https://kubernetes.default.svc
    namespace: prod
  syncPolicy:
    automated:
      prune: true        # Git에서 지운 리소스는 클러스터에서도 삭제
      selfHeal: true     # 누가 클러스터를 손으로 바꾸면 Git 상태로 되돌림
    syncOptions:
      - CreateNamespace=true
짚고 가기 selfHeal: true가 GitOps의 정수입니다. 누가 새벽에 kubectl edit로 손대도 Argo CD가 "Git이 정답"이라며 원상복구합니다. 인프라의 진실(source of truth)이 클러스터가 아니라 Git으로 이동한 것이죠.

Argo CD가 하지 않는 일: 이미지 빌드 ✗, ECR push ✗. Git manifest를 보고 EKS에 sync만 합니다. 역할 분담은:

도구역할
GitHub Actions빌드·테스트·Docker 이미지 생성·ECR push·manifest 태그 수정 (CI)
ECRDocker 이미지 저장소
Argo CDGit manifest 감시 → EKS 동기화 (CD)
EKSPod 실행
kubeletECR에서 이미지 pull
Deployment어떤 이미지를 몇 개 띄울지 선언

S9. CI는 GitHub Actions가 — 빌드·ECR push·manifest 갱신

App Repo의 워크플로 예시(빌드 → ECR push → Manifest Repo의 image 태그 수정):

name: Build and Update Manifest
on:
  push:
    branches: [ main ]
env:
  AWS_REGION: ap-northeast-2
  ECR_REPOSITORY: spring-api
  IMAGE_TAG: ${{ github.sha }}        # 이미지 태그 = 커밋 해시 (추적성)
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-region: ${{ env.AWS_REGION }}
          role-to-assume: arn:aws:iam::123456789012:role/github-actions-ecr-role
      - uses: aws-actions/amazon-ecr-login@v2
      - name: Build & tag & push
        run: |
          docker build -t $ECR_REPOSITORY:$IMAGE_TAG .
          docker tag  $ECR_REPOSITORY:$IMAGE_TAG 123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/$ECR_REPOSITORY:$IMAGE_TAG
          docker push 123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/$ECR_REPOSITORY:$IMAGE_TAG
      - name: Checkout manifest repo
        uses: actions/checkout@v4
        with:
          repository: your-org/spring-api-manifest-repo
          token: ${{ secrets.MANIFEST_REPO_TOKEN }}
          path: manifest-repo
      - name: Update image tag & commit
        run: |
          cd manifest-repo/apps/spring-api/prod
          sed -i "s|image: .*|image: 123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/spring-api:${IMAGE_TAG}|g" deployment.yaml
          git commit -am "deploy: spring-api ${IMAGE_TAG}"
          git push origin main          # ← 이 push를 Argo CD가 감지해서 EKS에 반영

여기서 GitHub Actions는 EKS에 직접 배포하지 않습니다. Actions = "빌드+ECR push+manifest 수정"(CI), Argo CD = "manifest를 보고 EKS 반영"(CD). CI와 CD가 깔끔히 분리된 게 GitOps의 미덕입니다.

S10. 직접 배포 vs GitOps — 한 장 비교 + 흔한 오해 4가지

직접 배포 (kubectl apply)GitOps 배포 (Argo CD)
개발자 PC에서 docker push → kubectl apply → EKS 변경git push → Actions가 ECR push → Manifest 수정 → Argo CD가 EKS sync
누가 했는지 추적 약함모든 변경이 Git에 기록
개발자 PC에 클러스터 권한 필요클러스터 직접 접근 권한 최소화
Git과 클러스터가 어긋날 수 있음Argo CD가 상태 차이를 계속 감시
롤백이 애매함롤백 = git revert

흔한 오해 4가지

  1. kubectl apply가 ECR에 이미지를 올린다? ✗ — 올리는 건 docker push. apply는 "이 ECR 이미지로 Pod 띄워라"는 지시일 뿐.
  2. kubectl apply만 하면 내 로컬 이미지가 EKS로 간다? ✗ — 먼저 ECR/Docker Hub/GHCR 같은 저장소에 올라가 있어야 pull 가능.
  3. Deployment가 GitOps다? ✗ — Deployment는 쿠버네티스 리소스. GitOps는 그 선언을 Git에 두고 Argo CD가 계속 맞추는 운영 방식.
  4. Argo CD가 이미지를 빌드한다? ✗ — 빌드·ECR push는 GitHub Actions(CI) 몫. Argo CD는 sync(CD)만.

S11. 한 문장 정리 + 비유 총정리

ECR은 Docker 이미지 창고이고,
deployment.yaml은 그 이미지의 주소가 적힌 배포 설계도이고,
kubectl apply는 설계도를 쿠버네티스에 제출하는 명령이고,
EKS는 설계도를 보고 ECR에서 이미지를 가져와 Pod로 실행한다.

쿠버네티스의 핵심 = '선언'(원하는 상태를 적는다)
GitOps의 핵심     = 그 선언의 '출처'를 Git으로 고정한다
Argo CD의 핵심    = Git의 선언과 클러스터의 실제 상태를 계속 맞춘다
Docker Image = 포장된 음식                  ECR          = 음식 창고
Deployment   = 몇 인분 준비할지 적은 지시서   Service      = 고객센터 전화번호
Ingress      = 백화점 정문 + 안내 데스크      kubectl apply= 점장이 직접 지시서를 현장에 전달
EKS          = AWS가 관리해주는 푸드코트       Argo CD      = 본사 지시서대로 현장을 계속 맞추는 감리자
Git          = 본사 지시서 보관소             GitOps       = 본사 지시서가 운영의 '정답'이 되는 방식

S12. 최종 — Spring Boot를 EKS에 올릴 때 반드시 구분할 5단계

1. 애플리케이션 빌드      (./gradlew clean bootJar)
2. Docker 이미지 생성     (docker build)
3. ECR에 이미지 업로드    (docker push)        ← EKS가 실행할 이미지는 미리 여기 올라가 있어야 함
4. 쿠버네티스 YAML 작성   (deployment/service/ingress)
5. EKS에 반영
      직접 배포  = 사람이 kubectl apply 로 클러스터를 바꾼다
      GitOps    = Git을 바꾸면 Argo CD가 클러스터를 바꾼다
마무리 한 줄 빈 우분투에 손으로 7단계(EC2 시뮬레이터) → git push 한 번(Railway) → 선언만 하면 알아서 유지(쿠버네티스) → Git이 곧 운영의 정답(GitOps). 같은 app.jar 하나가 사다리를 따라 올라갈수록, 내 손은 비고 시스템이 채웁니다.
